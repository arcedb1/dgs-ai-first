# GOVERNANCE.md — Governança de Specs (SDD) do NovaTech Assistant

Este documento rege como `requirements.md`, `plan.md` e `tasks.md` são criados, revisados, aprovados, nomeados, versionados e rastreados nos 5 módulos iniciais do projeto.

Princípio central: specs são artefatos vivos — evoluem junto com o código e as decisões do time, e cada evolução relevante deixa rastro em Git e no board.

## 1. Responsabilidades por artefato

| Artefato | Cria | Revisa | Aprova |
|---|---|---|---|
| requirements.md | Product Specialist | Tech Lead | Product Specialist |
| plan.md | Tech Lead | Product Specialist + Dev Sênior | Tech Lead |
| tasks.md | Dev + Copilot | Tech Lead | Tech Lead |

## 2. Nomenclatura e versionamento

- Nome de pasta = slug do módulo (kebab-case); arquivos sempre `requirements.md`, `plan.md`, `tasks.md`.
- Versionamento por status (rascunho, em-revisao, aprovado, revisao-solicitada) via cabeçalho no próprio arquivo.
- Histórico de mudanças vive no Git (commits dedicados por mudança de status, nunca reescritos).

## 3. Localização no repositório

Specs em `/specs/<modulo>/`, uma pasta por módulo, nome espelhando as pastas de código correspondentes em `/src/`.

## 4. Checkpoints humanos

- Gate 1 (requirements→plan): aprovado pelo Product Specialist.
- Gate 2 (tasks→implement): aprovado pelo Tech Lead.
- Gate 3 (code→merge) e Gate 4 (tests→deploy): referenciados do checklist de validation gates já existente.
- 4.1 Backup de aprovador: Dev Sênior assume Gate 2 temporariamente se o Tech Lead estiver indisponível, via fluxo de exceção de impacto Baixo, com registro explícito e revisão posterior do titular.

## 5. Rastreabilidade

- Mudança em requirements propaga para plan e tasks, com re-execução dos gates afetados.
- Regra prática: nenhuma task pode ser implementada se seu plan/requirements de origem não estiver aprovado.
- Rastro spec ↔ código ↔ teste mantido via convenção de commit message, PRs linkados e mapeamento verification criterion → teste.

## 6. Regra de ouro

Uma spec aprovada não é um contrato imutável — é o estado mais recente de um entendimento compartilhado. O que é imutável é o processo: toda mudança relevante passa pelo gate certo, aprovada pelo dono certo, com rastro em Git e no board.
